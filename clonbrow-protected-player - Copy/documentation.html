Protected Player
Architecture Guide

How a password-protected download can open a ClonBrow player, verify access with the cloud service, play labs and prototypes, and show a user watermark.

1. Overview

The recipient downloads a password-protected launcher package. After extracting it, they open ClonBrow Player.html. The player contacts the ClonBrow server, verifies the recipient's access, and opens the permitted features. The actual lab collection stays in server storage, rather than being bundled into that download.

Download password

Protects the ZIP archive while it is being shared. It is not the account password or API key.

Player sign-in

The launcher asks the recipient to sign in or enter a one-time invite/access code. The server validates it.

Play session

The server grants a short-lived, limited session to open approved labs and projects.

Developer API key

A separate credential for a project developer's API calls. Do not give a master or owner key to every player.

This requires an online server.The downloaded launcher can open while the owner's laptop is off, but sign-in, catalog access, API calls, watermark verification and hosted playback require the ClonBrow service and its storage to be running online.

2. Recipient journey

Owner creates a release

Choose which labs from the 262-file catalog are included, set the allowed users and expiration, and ask the service to create a release.

Service creates the protected ZIP

The ZIP contains a small launcher page and a non-secret release ID. It does not contain the lab source folder or a reusable API key.

Recipient downloads and extracts it

The recipient enters the ZIP password in a compatible archive tool. A web page cannot create a password-protected desktop folder or extract files by itself.

Recipient opens the player page

The launcher loads in the browser and asks for an account or a server-issued invite code. It sends the code to the API over HTTPS for validation.

Service grants a play session

The service checks that the invite is valid, unused or within its allowed use count, unexpired, and permitted to access the requested release. It returns a short-lived session, not the owner's API key.

Recipient plays features with a watermark

The catalog and player use the server API. The player shows the signed-in display name or invite label and a release mark. The service checks access on each protected operation.

3. Download package contents

Keep the portable package small. Treat every file delivered to a recipient as inspectable.

FilePurposeSecret?
ClonBrow Player.htmlLauncher UI, sign-in form, catalog/player shell and watermark area.No. Its HTML and JavaScript can be viewed.
release.jsonPublic release ID, service address and display settings.No. Do not put credentials here.
README.txtHow to enter the download password, open the player and get help.No.
Do not bundle the 262 source files. Store approved feature files and assets on private server storage. The launcher requests an authorized feature from the service after sign-in.

The service should create a per-recipient invitation independently of the ZIP password. That lets the owner revoke one person's access without reissuing every recipient's download. If the ZIP password itself is shared, it cannot identify which person opened the archive.

4. Watermark behavior

After successful access validation, show a visible overlay in the player and, where practical, inside the active lab view:

  • Use a display name or privacy-safe account label, not an email address unless necessary.
  • Repeat a faint diagonal watermark on the main viewing area and keep a compact label visible in the header.
  • Use server-issued session information; do not trust a recipient-editable localStorage name.
  • Refresh the session periodically. On expiration or revocation, stop API requests and return to the access screen.
  • Watermarking discourages casual redistribution. A determined user can still crop, cover or record a screen.
Watermark is attribution, not access control.The API must enforce account, release, feature and expiry permissions even if the overlay is removed.

5. Using ClonBrow from another project

The reusable integration is an HTTPS API base URL plus a user- or project-scoped API key. The key is issued by the deployed service. Keep it in a trusted backend for production apps; never publish an owner key in client HTML.

JavaScript example

const CLONBROW_API = "https://api.your-domain.example/api/v1";
const apiKey = getKeyFromYourTrustedBackend();

const response = await fetch(
  CLONBROW_API + "/labs",
  { headers: { Authorization: "Bearer " + apiKey } }
);

if (!response.ok) throw new Error("ClonBrow API request failed");
const labs = await response.json();
console.log(labs.items);

The following routes are the proposed cloud contract. Feature browsing can expose the 262-file catalog, including labs, simulations, tools and games, subject to the caller's release permissions.

These are API specifications, not an existing hosted service. A route only works after it is implemented and deployed. Never put a real API key in a public demo or a downloadable HTML file.

6. Server components

API service

HTTPS endpoints, authentication, permissions, rate limits, access expiry, key rotation and revocation.

Database

Users, normalized unique names, hashed invite codes and API keys, releases, grants, sessions, projects and audit events.

Private object storage

Protected lab files, assets, release packages and project uploads. Use expiring signed links or an authenticated proxy.

Player hosting

Serve authorized features and project deployments while the owner's computer is offline.

Core data records

users(id, normalized_name UNIQUE, status, created_at)
invites(id, code_hash UNIQUE, release_id, max_uses, uses, expires_at, revoked_at)
releases(id, owner_id, title, feature_ids, status, created_at)
grants(id, release_id, user_id, expires_at, revoked_at)
sessions(id, user_id, release_id, token_hash, expires_at, revoked_at)
api_keys(id, owner_id, key_hash, prefix, scopes, expires_at, revoked_at)
features(id, title, kind, storage_key, version, visibility)
projects(id, owner_id, storage_key, play_url, state, created_at)
audit_events(id, actor_id, action, target_id, created_at, safe_metadata)

Enforce single-use invite redemption and unique account names in database transactions with unique constraints. Store hashes for long-lived secrets; return newly issued API keys only once. Add quotas, backups and account/key revocation.

7. Access and security rules

  • Use HTTPS for portal, API, package delivery and player hosting.
  • The ZIP password protects the download archive. It does not prove a recipient's identity and should not be the only authorization check.
  • Redeem a per-recipient invite code at the server. Make codes random, expiring, scoped to a release and limited by use count.
  • Issue short-lived play-session tokens. Do not expose the API owner's key to players.
  • Check authorization on every catalog, feature, project and flashcard request. A hidden button or guessed URL is not an access check.
  • Hash API keys and invite codes at rest; support expiry, rotation and revocation. Do not log their plaintext values.
  • Validate ZIP entries to prevent path traversal. Limit archive size, file types and build time. Run uploaded projects in isolated sandboxes.
  • Use CORS allowlists for the player and API client sites. Apply rate limits and monitor abuse without recording secrets.

8. What “no coding files” can and cannot mean

Achievable: Do not put the original 262 HTML files, source archive or a long-lived API key in the password-protected download. Keep these in private server storage. The downloaded folder can contain only the launcher and a public release ID.
Not achievable with a normal browser page: A browser must receive enough HTML, JavaScript, CSS or other instructions to display and run an interactive lab. A recipient can inspect files sent to their browser using developer tools or network downloads. Obfuscation, disabling right-click and a password form do not provide reliable source protection.

If source secrecy is a strict requirement, the labs need to be redesigned to run on the server and stream rendered output or use a remote interactive session. Simply placing current HTML labs behind login, in an iframe or behind an API does not hide their delivered source. That server-rendered architecture is more expensive and may require rebuilding the prototypes.

Also, a static HTML file cannot launch Terminal, install software, create a protected folder, or guarantee that an archive stays encrypted after extraction. The recipient uses an archive tool to unlock the ZIP, then opens the launcher in a browser.

9. Build and deployment sequence

  1. Choose a cloud host and configure a domain with HTTPS.
  2. Implement the API, database, private object storage and player hosting; configure backups and monitoring.
  3. Import and review the prototype catalog. Decide which pages are safe to publish and which external services each page requires.
  4. Build the release manager: choose features, create recipients/invites, set expiry and issue a password-protected launcher ZIP.
  5. Build the player: redeem invite, obtain a limited session, show the server-verified watermark, list permitted features and check session expiry.
  6. Implement the developer API key flow separately: scoped key issue, one-time display, hashed storage, rotation and revocation.
  7. Test revoked invites, expired sessions, unauthorized feature IDs, duplicate names, oversized ZIPs and laptop-off playback before sharing releases.
Cloud host credentials are required to deploy.This repository does not include a hosting account, domain, database credentials, or a live project/player service.

10. Current project status

This repository contains the prototype HTML collection and a local Node API for catalog and flashcard experiments. That local service binds to the developer's computer and is not the shared cloud service described above. The Cloud Portal is a static client scaffold; it does not create accounts, invites, API keys, encrypted packages or hosted play sessions on its own.

Result: this document describes the complete target behavior and backend contract. The protected player and cloud service still need to be built and deployed before recipients can use the proposed flow.
